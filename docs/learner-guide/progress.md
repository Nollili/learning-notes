# A sustainable study cycle and progress record

[Guide home](./) · [Existing evidence requirements](../practice/learning-projects.md#retain-a-real-evidence-record)

Read a bounded section → predict or trace a concrete example → attempt independently → run meaningful checks → investigate one failure → record evidence → revisit the explanation. A loop ends with a smaller uncertainty or a better counterexample, not necessarily with a completed project. Save a working increment before widening scope. Start the next bounded exercise once its inputs and invariants make sense; defer later service/provider/deployment requirements until integration.

## Keep five statuses separate

| Status | What it means | What it does not prove |
|---|---|---|
| Material read | You read named sections and recorded a question/summary | Implementation or recall |
| Exercise attempted | Your own revision exists, with a stated contract | Correct behavior |
| Checks passed | Named commands/cases passed on that revision | Unchecked boundaries, independent explanation or production readiness |
| Concept demonstrated independently | You explain/trace/modify it without following the worked solution and defend a counterexample | Universal mastery |
| Remaining uncertainty | Explicit unresolved behavior and next investigation | A failure of the study process |

Do not infer a later status from an earlier one. Reference verification belongs in the reference ledger, not your learner record. All fields below intentionally start outstanding/unrecorded.

## Copy this template into your own evidence notebook

```text
Track / existing assignment ID / bounded milestone:
Lesson links and sections:
Material read: outstanding; actual sections/date/own explanation:
Exercise attempted: outstanding; own directory/revision and chosen contract:
Checks passed: unrecorded; command/case, expected vs observed, exit result:
Concept demonstrated independently: unrecorded; trace/change/explanation:
Remaining uncertainty / next concrete action:

Reading prerequisites satisfied / still uncertain:
Implementation dependencies satisfied / outstanding:
Source revision and runtime/compiler/lock/config identities:
Synthetic input bytes / seed / schedule / workload:
Negative case that detected a real defect:
Correction and retest tied to final revision:
Resources opened / owner / close and natural-exit observation:
Safe evidence files (no credentials/private logs):
Boundary-specific evidence (UI, SQL race, receipt, restore, etc.):
Performed checks versus unperformed environments:
Reviewer/approval outcome: not performed unless actually observed
Next milestone and observable entry criterion:
```

Record exact case outcomes rather than “done.” A screenshot supports visible state, not transaction isolation. A mock supports adapter contracts, not live provider quality. A finished build supports those candidate bytes, not a later edit. Keep unknown costs/outcomes unknown; do not convert them into zeros or success.
