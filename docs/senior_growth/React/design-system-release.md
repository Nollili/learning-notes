# Design Systems: Stories, Visual Review and Consumer Migrations

## Maintained documentation is part of the contract

Start with the [Button and token contracts](./design-system-contracts.md). A component page should state purpose, appropriate alternatives, supported props/defaults, keyboard/focus rules, naming guidance, theme hooks, responsive behavior, examples and migration policy. Autogenerated prop tables cannot explain why a control exists or which combinations are invalid. Assign a maintainer and update stories in the same change as the component; consumers need a reproducible story rather than a screenshot pasted into a wiki.

Baseline checked 2026-10-21: Storybook **10.6** docs, React/Vite framework, CSF3 stories. Keep Storybook packages/addons on compatible versions in a separate practice consumer. This notes repository does not install Storybook. Configure the official React/Vite framework, include `*.stories.tsx`, import the generated global tokens in preview, and set a known light root theme. Configure the documented Vitest addon/browser provider when running interaction tests; writing a play function does not prove it ran.

```tsx
// Button.stories.tsx — alongside Button.tsx from the contract lesson
import type { Meta, StoryObj } from '@storybook/react-vite';
import { expect, fn } from 'storybook/test';
import { Button } from './Button';

const meta = {
  title: 'Controls/Button', component: Button, tags: ['autodocs'],
  args: { children: 'Save draft', onClick: fn() },
  parameters: { layout: 'centered' }
} satisfies Meta<typeof Button>;
export default meta;
type Story = StoryObj<typeof meta>;

export const Primary: Story = {
  play: async ({ args, canvas, userEvent }) => {
    await userEvent.click(canvas.getByRole('button', { name: 'Save draft' }));
    await expect(args.onClick).toHaveBeenCalledTimes(1);
  }
};
export const Secondary: Story = { args: { variant: 'secondary' } };
export const Disabled: Story = {
  args: { disabled: true },
  play: async ({ canvas }) => {
    await expect(canvas.getByRole('button', { name: 'Save draft' })).toBeDisabled();
  }
};
export const LongLabel: Story = {
  args: { children: 'Save all changes and return to the course overview' }
};
```

Give additional stories explicit light/dark wrappers (with the same theme CSS as production), a narrow viewport, keyboard focus and a button inside a form. Do not invent a loading prop the API lacks. Add an integration story for a consumer that owns pending/error state. Avoid calling the real production service; use deterministic fixtures at the request boundary and reset mocks/state between stories. Button's action spy should be fresh/reset per test under the configured runner; do not share accumulated counts across a hand-written runner.

## Distinguish the checks

| Layer | What it can establish | Important blind spot |
|---|---|---|
| Type consumer fixtures | Public prop/ref exports compile; invalid props fail | JavaScript callers and real interaction |
| Play interaction | A defined scenario invokes handlers and produces expected DOM | Real keyboard/browser integration beyond that scenario |
| Automated accessibility | Detected rule violations for the rendered state | Correct words, focus journey and full WCAG coverage |
| Visual diff | Pixels changed for captured environment/state | Whether change is intended, accessible or behaviorally correct |
| Consumer integration | Routing/forms/styles interact with the library | Other consumers/environments not exercised |

Use a visual service compatible with Storybook (for example Chromatic) or an existing browser screenshot runner. Primary workflow here is reviewed Storybook snapshots; no account/upload is required by this lesson. Pin browser/OS/fonts, viewport, locale, timezone, color mode and fixture data. Wait for fonts/assets, disable nonessential animation in test mode and avoid live timestamps/random IDs. Capture focus deliberately; never remove focus CSS to quiet a diff. Missing fonts and changed browser antialiasing can create noise: investigate environment drift before approving hundreds of baselines.

In a PR, attach baseline/current/diff for each supported state and the design reason. Maintainer checks clipping, alignment, wrapping, focus, contrast and unintended downstream changes; reviewer approves an intentional baseline only after interaction/type checks pass. An unexplained visual difference blocks the change. Record approved baseline revision and retain rejected diffs for diagnosis. Regenerate only affected stories; a blanket “accept all” conceals regressions. Pixel thresholds are a noise policy, not a correctness guarantee. Theme/interaction combinations should come from risk analysis: both variants × themes, disabled, keyboard focus, narrow width and long label are a useful starting set, not proof of complete coverage.

## A consumer migration case

Suppose a hypothetical published `@acme/ui` 2.3 Button exposes `tone="solid" | "quiet"`. These fictional package versions illustrate a migration, not this repository's history. The desired API is `variant="primary" | "secondary"` from the companion lesson.

1. In **2.4**, introduce `variant` while retaining `tone`; mark `tone` deprecated in the public types and docs. Map solid→primary and quiet→secondary internally. Reject mixed props in TypeScript; specify deterministic precedence for JavaScript callers (new `variant` wins, with a development warning). Do not silently change the default appearance. Test both compatibility paths.
2. Changelog: “Added variant; tone deprecated; removal planned for 3.0.” Include before/after code, unchanged defaults/ref/native props and affected token aliases. Update consumer inventory with owner, current version and adoption evidence.
3. Offer a conservative codemod, then inspect the diff. Literal usages can be migrated; dynamic values/spreads/wrappers need human reasoning. A replacement of the word `tone` across the repository would damage unrelated APIs.
4. Pilot 2.4 in one representative form and toolbar consumer; compile, run stories and integration tests. Resolve style/ref/focus regressions before wider adoption.
5. In **3.0**, remove `tone` only after the documented migration window. Publish release notes for the breaking contract. A new major does not repair consumer code automatically. Keep the last compatible release available; rollback means restoring a tested consumer lockfile/build artifact, not overwriting an existing published version.

SemVer applies to the declared public API: compatible fixes are patch, compatible additions/deprecations minor, incompatible removals major after 1.0. CSS variables, DOM hooks and behavior may be public too. Even a design correction that changes wrapping can require a consumer migration policy; choose version impact from the documented compatibility promise. Versioning alone cannot detect breakage.

```tsx
// Before: consumer on 2.3
const before = <Button tone="quiet" onClick={save}>Save</Button>;
// After: consumer on 2.4 or 3.0
const after = <Button variant="secondary" onClick={save}>Save</Button>;
```

### A small executable AST codemod with an explicit safety envelope

This teaching transform accepts a deliberately limited fixture format: imports plus exported single `const` declarations initialized with **static JSX only**. It recognizes direct named Button imports, including aliases. Anything dynamic or structurally more complex returns `review` with no changes. Expand it only with scope analysis and regression fixtures; it is not a project-wide production migration engine. Run in a scratch copy, review the patch and retain skipped paths.

```js
// migrate-button.cjs — requires @babel/parser in the practice workspace
const { parse } = require('@babel/parser');
function migrateButton(source) {
  const ast = parse(source, { sourceType: 'module', plugins: ['jsx', 'typescript'] });
  const names = new Set();
  for (const statement of ast.program.body) {
    if (statement.type !== 'ImportDeclaration') continue;
    if (statement.source.value !== '@acme/ui' || statement.importKind === 'type') continue;
    for (const spec of statement.specifiers) {
      if (spec.type === 'ImportSpecifier' && spec.imported.name === 'Button' &&
          spec.importKind !== 'type') names.add(spec.local.name);
    }
  }
  if (!names.size) return { status: 'unchanged', source };
  const edits = [];
  function visit(node) {
    if (node.type === 'JSXText') return;
    if (node.type !== 'JSXElement') throw new Error('Dynamic or unsupported JSX');
    const opening = node.openingElement;
    if (opening.name.type !== 'JSXIdentifier') throw new Error('Complex tag');
    const attrs = opening.attributes;
    if (attrs.some(a => a.type !== 'JSXAttribute' ||
        a.name.type !== 'JSXIdentifier' ||
        (a.value !== null && a.value.type !== 'StringLiteral')))
      throw new Error('Dynamic attribute or spread');
    if (names.has(opening.name.name)) {
      const tones = attrs.filter(a => a.name.name === 'tone');
      if (tones.length > 1 || (tones.length && attrs.some(a => a.name.name === 'variant')))
        throw new Error('Conflicting props');
      if (tones.length) {
        const attr = tones[0];
        const map = { solid: 'primary', quiet: 'secondary' };
        const value = attr.value?.value;
        if (!Object.hasOwn(map, value)) throw new Error('Unknown tone');
        edits.push({ start: attr.start, end: attr.end,
          text: `variant="${map[value]}"` });
      }
    }
    node.children.forEach(visit);
  }
  try {
    for (const statement of ast.program.body) {
      if (statement.type === 'ImportDeclaration') continue;
      const d = statement.type === 'ExportNamedDeclaration' ? statement.declaration : null;
      if (!d || d.type !== 'VariableDeclaration' || d.kind !== 'const' ||
          d.declarations.length !== 1) throw new Error('Unsupported statement');
      const item = d.declarations[0];
      if (item.id.type !== 'Identifier' || names.has(item.id.name) || !item.init)
        throw new Error('Unsupported binding');
      visit(item.init);
    }
  } catch (error) {
    return { status: 'review', reason: error.message, source };
  }
  let result = source;
  for (const edit of edits.sort((a, b) => b.start - a.start))
    result = result.slice(0, edit.start) + edit.text + result.slice(edit.end);
  return { status: edits.length ? 'changed' : 'unchanged', source: result };
}
module.exports = { migrateButton };
```

Example fixture: `import { Button as Action } from '@acme/ui'; export const Example = <Action tone="quiet">Save</Action>;` becomes `variant="secondary"`. A wrapper function, expression child, event handler, spread or `tone={choice}` is deliberately skipped; the real before/after handler example above needs manual migration. Parse errors are caller failures: catch/report the filename and do not overwrite it. Write transformed output only after successful parsing and review; never partially apply a file. Running twice must produce unchanged output on the second pass. Imported binding resolution here relies on the narrow allowed program structure; lifting those constraints without a proper scope-aware traversal is unsafe.

## Practice and acceptance

Create Button stories in the separate consumer and configure its supported runner. Acceptance: Primary interaction runs, Disabled is checked, long label/narrow viewport render, both theme sets have approved baselines, a deliberately broken padding/focus change produces a rejected diff. Keep the runner output and human review evidence; do not claim a snapshot proves accessibility.

For migration, test direct and aliased imports, both literal values, unrelated library imports, mixed props, unknown literal, spread, dynamic value and unsupported wrapper. Acceptance: safe fixtures transform exactly, manual cases preserve bytes and report a reason, a second run is idempotent, consumer typecheck and behavior tests pass. Add one real consumer migration record and rollback rehearsal using local artifacts. Publishing/pushing is not part of the exercise. All learner practice remains required.
